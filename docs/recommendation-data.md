# 分阶段推荐与数据仓库（当前源码 1.12.1）

用户确认的目标：加载页读取双方阵容，只显示装备；游戏中任何经过验证的已选来源更新统一会话后，立即重算装备和后续海克斯。候选卡片识别不是已选确认。自动选择确认仍属于独立实验功能，本次推荐改造不代表该识别链路已经实战通过。

## 数据流与职责

1. `RecommendationRepository` 为当前英雄预取公开聚合数据，不请求玩家身份、对局记录或当前敌方构筑。
2. `build-evidence.js` 负责同英雄、同模式、同版本的统计适配，严格区分总体、单海克斯条件和组合统计。
3. `adaptive.js` 在统计候选上应用本局装备可用性、已选限制及有效双方阵容；敌方伤害类型仍是机制线索，不是实测伤害占比。
4. `recommendation-policy.js` 统一三选一、英雄适配与后续推荐排序。英雄胜率页原始胜率差榜保持原口径。
5. `BackgroundSidebar` 输出权威计划；主窗口只在英雄、局次、修订、已选顺序、路线、阶段及时间全部一致时采用，与原生侧栏使用相同计划。无法匹配时回退同一纯引擎，不复用旧计划。

加载计划的 `nextAugments` 为空，网页与原生侧栏均不显示识别、已选和后续海克斯区域。进入实战后恢复这些区域。已有字体、布局、收放、焦点、快捷键和每次启动侧栏位置规则保留。

## 主数据与辅助来源

- AramHex 随包快照只用于同口径英雄持有海克斯胜率；由原始 wins/games 计算，不使用旧版本选择率冒充当前选择率。保留其 3,000 场低样本规则和 PBE 隔离。
- ARAMKit 当前英雄详情的 `items.filtered` 为本模式排除关联项后的基础装备样本，仍是 Mayhem，不是普通 ARAM、也不等于无海克斯的随机试验。
- 选择后使用最近确认海克斯对应的英雄＋单海克斯条件装备。多个已选不会把各条件胜率平均成联合胜率；其他已选通过机制兼容过滤参与。
- 来源公开的双海克斯组合只有有限前10组。共同出现证据与单海克斯装备分别保留，不能拼成双海克斯条件出装。
- OP.GG 普通 ARAM 的公开 `/items` 页面提供独立单件及鞋子统计。只有同英雄、同模式、同版本的完整单件记录才参与辅助评分；三件套胜率不拆给单件。
- 普通 ARAM 无有效数据时才尝试召唤师峡谷；仍缺则本模式 100%。SR 的地区、分段和默认位置单独保留，不能称为全分段或全位置。

配置的 80:20 是**各模式内胜率排名得分**的权重，不是把两个模式胜率混成“综合实测胜率”。只在两源都有相同装备的有效记录时混合；辅助源未记录的项目保持本模式 100%，不是辅助源胜率为零。输出包含全局覆盖、单件实际权重、原始胜率及来源，`mixedWinRate` 始终为 null。

核心三件套和购买顺序被独立保留供后续展示；当前本局展示是经阵容筛选的装备选项，不能把不同单件拼接称为一套经过实测的六神装。

## 排序规则与可扩展点

用户确认：胜率接近时，依次比较机制性、成长/百分比、固定数值；低选择率只作末位比较。数值顺序是全能吸血、生命偷取、百分比穿透、暴击、百分比攻击、高额固定攻击、固定穿透、攻击、生命、护盾；英雄特殊机制允许例外。

当前产品默认参数（不是游戏规则或用户指定数值）：

- 胜率接近窗口：1个百分点，以组内最高胜率锚定，避免两两比较产生循环排序。
- ARAMKit 和辅助装备可信样本：至少200；这不是统计显著性保证。AramHex 仍遵守来源更严格的3,000场规则。
- 高额固定攻击分类阈值：60攻击力。

默认规则是纯JSON结构的 `DEFAULT_RECOMMENDATION_POLICY`，可通过 `augmentOverrides`、`championOverrides` 配置带理由的人工审阅例外。未知描述保留 unknown，不能只凭名称推断机制。本轮规则并未完成244个常规条目的人工全量分类；无可信胜率时明确按机制适配回退，不生成伪胜率。

1.12.1 由 `engine.js` 的共享文本规则识别 `noUltimate / requiresUltimate`：明确禁止自身终极技能的已选，与收益完全依赖该技能的候选存在冲突；候选反过来禁用已有海克斯需要的终极技能时也相同。`getSynergy`、`recommend`、三选一与直接排名、实战后续建议都在比较胜率前应用该约束，不按英雄 ID 写例外。“回归基本功”与“最终形态”“终极刷新”等因此不能再因较高统计胜率进入优先推荐。仅提及终极技能、基础技能收益、其他独立触发、自动获得的借用技能或兼有独立收益的效果，不据此整项禁用；装备的独立属性收益保留。

## 已选来源与人工纠正

手动和屏幕观察继续走共同提交路径。Collector 若实际返回完整映射的明确已选 IDs，服务端仅在本局、实战、当前英雄、模式与时间有效时接受；已有已选必须是新快照的有序前缀，不能把与人工确认冲突的快照当新一轮追加。空或不可读快照不删除记录。

人工删除、替换或重排已选后，阻止该局后续快照自动追加；保护标志随本局记录落盘，重启保留，新局清空。屏幕有证据的逐轮确认与人工选择继续可用。尚未取得真实游戏已选API字段或Overwolf事件时，这些接入测试只是契约验证，不代表真实来源已上线。

## 缓存、更新及失败策略

- 索引仓库沿用既有数据目录，原子保存 `recommendation-cache-v1.json`，不迁移现有设置或数据库。
- 最多3位英雄、24小时TTL；只按当前英雄请求，不全库抓取。公开聚合缓存不加入源码或安装包。
- 两源独立状态、时间与失败退避；辅助失败不抹掉本模式。旧对象可保留在缓存中，但 stale 或 loading 期间的旧统计不参与新的统计推荐。
- OP.GG HTML解析只解码JSON，不运行网页脚本。页面结构、身份或版本不符时返回缺失；401/403/429停止回退并等待30分钟，不绕过限制。1.12.1 为每个仓库保留一个延迟初始化的参考来源及其初始化 promise，使换英雄、60秒级仓库重试或同时初始化都不能重置该等待期；不同仓库实例独立。注入客户端、时钟、版本与来源校验、24小时新鲜度守卫继续适用。
- 缺样本、低样本或读取失败时清楚标为机制参考，不把机制装备伪装成实战条件装备。
